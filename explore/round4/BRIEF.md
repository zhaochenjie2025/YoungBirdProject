# 第四轮 · 以 A（拍立得）为底稿派生版本 M

## 背景

团队表决选定 **A 拍立得** 作为方向。现在要在 A 的基础上派生出定稿版本 M。

**底稿**：`explore/round1/dir-a-拍立得/index.html`（57 KB，两轮带技能质询后 7.5/10）
**产出**：`explore/round4/dir-m-定稿/index.html` + `NOTES.md`

## 一、不可动摇的（这是团队投票的基础）

1. **A 的母题与识别特征**必须保留：一餐 = 一张即时成像相纸；整套界面是暗房；相纸是唯一发光物。
2. **A 的工艺**必须保留：相纸自发光与实体厚度、手写 chin、显影接触印相条、车削机械快门、35mm 齿孔与帧号。
3. 如果某个改动会削弱上面两条，就不要那样改。

## 二、需要解决的问题（要达成什么，不预设怎么达成）

以下是这一版必须解决的**问题清单**。**具体方案由你判断**——你有技能、有参考库、看过十二个方向的成品，比我有资格定这些。

### 问题 1：七日视图读不出营养构成

团队原话：「七日图显示卡路里及营养成分占比」。

现状：A 的周视图是纯胶片条，只有每天的总热量，看不出蛋白/脂肪/碳水的构成。

你要解决的是：**让用户在周视图里同时读到「每天吃了多少」和「这天的构成是什么」**，而且要在 A 的胶片语言里做，不能变成一张普通图表。

参考：`explore/round3/dir-k-苹果/index.html` 的周柱（这是被验证有效的结构），
以及 `explore/round2/dir-j-日系/index.html` 的灰阶堆叠柱、
`explore/round2/dir-e-简约/index.html` 的柱 + 刻度 + 数值标签。

**但怎么把柱状结构翻译成胶片语言、用什么编码区分三种营养素、要不要保留胶片语法、保留多少——你自己定，并在 NOTES 里说明理由。**

### 问题 2：没有分享功能（最大增量）

团队原话：「简约且具有年轻人喜好特性：便于分享，有成就感的分享桌面如 A 拍立得」

现状：A 完全没有分享功能。

你要解决的是：
- 一餐 / 一天 / 一周能被做成**可以存下来发出去的东西**
- 这个东西要**有成就感**——不是截个图，而是值得炫耀的
- 要做到「存成图片就能发」的程度

**技术约束**：不能引 html2canvas 等库（零外部依赖）。用 Canvas 绘制或 SVG 序列化都行，你选。

**形式你自己定**：既然 A 的核心是拍立得，分享物可以是一张拍立得、一张胶片条、一张周报、或者其他更合适的东西。**不要照我说的做，想出你认为最好的那个。**

### 问题 3：识别确认页的风格

团队原话：「那种可以直接导入照片，然后把食物抠出来的页面可以小清新一点，或者是卡通一点」

你要解决的是：**「拍照 → 看识别结果 → 选菜」这一段的观感要更轻松、更亲和**。

注意边界：
- 团队说的是**这个特定页面**，不是全站换风格
- 但怎么让它和暗房主基调共存，是你需要想清楚的设计问题——
  可以是渐变过渡、可以是明确的场景切换、可以是保留暗房但让这个页面有独立的氛围。
  **不要生硬换皮，也不要为了统一而忽略这条意见。**

## 三、可以从其他方向借的东西（不是必须，自己判断要不要）

- **K** 的应用外壳布局：内容区自己滚动、底边止于导航上沿，根治固定导航遮挡内容的问题。（这条建议直接采用，是工程正确性问题）
- **K** 的周柱：y 轴刻度、平均虚线、未记录日的表达方式
- **E / J** 的克制版周视图：柱顶数值、刻度、灰阶编码
- **L** 的 die-cut 贴纸感：白边 + 微旋转，可能适合分享卡这类小元素
- **E / G / L** 的数字滚动（Number Ticker 的原理）：让数值变化有反馈
- **J** 的做法：可读性用机器断言验证（柱高与标值一致、分段之和等于总高）

## 四、硬约束

- 手机优先 390×844，适配 360 和 320
- 单文件 ≤120KB（底稿 57KB，加功能后要控制）
- 零外部依赖：不引库、不联网、不用 CDN 字体、不引外部图片
- **插画用公开素材**（undraw / SVGRepo / Twemoji / Lucide 等 CC0 或宽松许可），
  内联进 HTML，**不要在 NOTES 之外自己硬画 SVG 插画**。必须在 NOTES 记录来源与许可。
- 动画只用 transform/opacity，尊重 prefers-reduced-motion
- 390/360/320 无横向溢出，console 零报错
- **底部导航零遮挡**：用矩形相交验证（三档尺寸 × 静止态 + 滚到底），不要用肉眼

## 五、流程

1. 加载 `creative-frontend` Skill
2. 读底稿 A 的完整代码与 NOTES
3. 按需读其他方向的实现
4. 自己做方案决策，写进 NOTES **并说明为什么这样选、否决了什么**
5. 派生质询代理（`s39o-aesthetic-critic`，`model: haiku`），prompt 最前面必须先加：

```
## 必做第一步（在你的裁决之前完成）
1. 调用 Skill 工具加载 `creative-frontend`
2. 读 `~/.claude/skills/creative-frontend/references/scaffolds-and-refs.md`
3. 读 `~/.claude/skills/creative-frontend/references/craft-and-perf.md`
4. 读 `~/.claude/skills/creative-frontend/references/review-checklist.md`

你的裁决必须以上述文件里的工艺密度标准、3D 精度线、Sou39O 审美品味原话校准为标尺，
给出升维方向时必须点名参考库里具体的组件机制，不能只凭个人感觉。
```

6. 按质询单返工，最多 2 轮
7. 自检 + 汇报

## 六、汇报要求（≤30 行）

1. 保留了什么（A 的母题与工艺）
2. 三个问题各自你选了**什么方案**、为什么这样选、否决了哪些备选
3. 分享功能：生成方式、能不能真存成图片、你实测过没有
4. 识别页：怎么和暗房主基调共存的
5. 质询轮次与结论
6. 自检结果（含矩形相交数据）
7. 未做到的和原因
